# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

macro-hub visualizes macro-economic trends from multiple data sources (Riksbanken, Eurostat, Federal Reserve, Swedish Parliament, Valmyndigheten, SCB). It consists of:

- **macro-backend/** — Java 25 / Spring Boot 4.1.2 backend, a Maven reactor (parent `pom.xml` and `mvnw` here):
  - **macro-platform/** — library with the `scrape` core and `shared` (no application class; its only migrations are `db/platform`, which every service runs first)
  - **regional-statistics-service/** — SCB DeSO/RegSO statistics: the `regionalstatistics` module, `RegionalStatisticsApplication`, its own migrations and properties
  - **macro-series-service/** — the chart series: the `macroseries` module, `MacroSeriesApplication`, its own migrations and properties, and the Riksbanken and Fed keys
  - **parliament-service/** — Riksdagen: the `parliament` module, `ParliamentApplication`, its own migrations and properties
  - **election-service/** — Valmyndigheten's elections: the `election` module, `ElectionApplication`, its own migrations and properties
  - **auth-service/** — accounts, sessions and the JWTs: the `auth` module, `AuthApplication`, its own migrations and properties ([ADR 0010](docs/adrs/0010-own-auth-service-with-sessions-and-jwts.md))
  - **acceptance-tests/** — black-box tests of the built images, only over HTTP through the gateway (no main code, and it depends on no other module)
- **macro-frontend/** — Vite + React 18 + TypeScript + shadcn-ui dashboard (formerly the separate `macro-view-hub` repo, merged in via `git subtree`)
- **macro-backend/macro-infra/** — Docker Compose files (`docker/`), `scrape-all.sh`, `load-test.sh`, `acceptance-test.sh` and the CI-only `compose-smoke.sh` (`scripts/`), and the k6 load test (`load-tests/`)

## Services

The backend is one service per domain ([ADRs](docs/adrs/README.md), and the [migration guide's last version](https://github.com/KGjertsson/macro-hub/blob/584119f/docs/microservice-migration-guide.md) for how it got here).

| | `regional-statistics-service` | `macro-series-service` | `parliament-service` | `election-service` |
| --- | --- | --- | --- | --- |
| Domain | `regionalstatistics` | `macroseries` | `parliament` | `election` |
| Port (container and host) | 8082 | 8083 | 8084 | 8085 |
| Database and role | `regional_statistics` | `macro_series` | `parliament` | `election` |
| Compose service | `regional-statistics` | `macro-series` | `parliament` | `election` |
| Manual scrape paths | `/macro-analyzer/scrape/regional-statistics/{enqueue,enqueue-all,scrape-from-queue}` | `/macro-analyzer/scrape/macro-series/{...}` | `/macro-analyzer/scrape/parliament/{...}` | `/macro-analyzer/scrape/election/{...}` |

`auth-service` (domain `auth`, port 8086 on the host's 127.0.0.1 only, database, role and Compose service `auth`) is the exception to much of what follows: it has no scraping, so no `db/platform`, queue, crons or scrape paths, see "Accounts and login".

Every service runs `db/platform` (from `macro-platform`, history table `flyway_platform_schema_history`), then its own `db/migration`. Everything below about a "module" holds in all of them. The Java base package `com.kg.macroanalyzer` and the URL prefix `/macro-analyzer` are the project's old name, and every service keeps them.

**Databases:** every service's properties and every jOOQ codegen profile default to the Compose Postgres on `localhost:5432`, and each service's `BaseConfigurationTest` pins that. To use another database, pass the URL deliberately (`SPRING_DATASOURCE_URL`).

## Build & Test Commands

### Toolchain requirements

- **JDK 25** for the backend (installed via SDKMAN). If `java -version` isn't 25 (e.g. an IDE exported an older `JAVA_HOME`), set `JAVA_HOME=~/.sdkman/candidates/java/current` for Maven commands.
- Lombok is registered under `annotationProcessorPaths` in the compiler plugin because JDK 23+ no longer runs annotation processors found on the classpath; without it the build fails with `cannot find symbol` errors (`log`, getters/builders). Any other compile error produces the same errors too, because Lombok's generated code goes missing, so filter them out to find the real one.
- **Node 20.19+ or 22.12+** for the frontend (Vite 7). Node 18 fails with `crypto.hash is not a function`.
- `mvnw` and the `*.sh` scripts are committed as executable. The root `.gitattributes` keeps them (and `.githooks/*`) LF even under `core.autocrlf=true`, so `./mvnw ...` works; if an old checkout still has CRLF copies, delete them and `git checkout -- .` to refresh.
- Docker must be running for Postgres and for `mvn test` (TestContainers).

### Starting the local stack (in this order)

**Default: Docker Compose** (from repo root; see "Docker" below for what it runs):

1. **Check what is already running:** `docker ps` and `lsof -nP -iTCP -sTCP:LISTEN | grep -E ':(8081|8082|8083|8084|8085|8086|5173)'`. On a fresh clone, also `cp macro-backend/macro-series-service/.env.example macro-backend/macro-series-service/.env`: step 3 fails with `couldn't find env file` without it. The keys in it can stay empty until you scrape Riksbanken or Fed series.
2. **Build the backend images:** `(cd macro-backend && ./mvnw clean package && docker build -t regional-statistics-service regional-statistics-service && docker build -t macro-series-service macro-series-service && docker build -t parliament-service parliament-service && docker build -t election-service election-service && docker build -t auth-service auth-service)`.
3. **Start everything:** `docker compose --env-file macro-backend/macro-series-service/.env -f macro-backend/macro-infra/docker/docker-compose-all.yml up -d --build`. Open `http://localhost:8081`. Flyway migrations run on startup. On an **empty** volume, Postgres creates the `regional_statistics`, `macro_series`, `parliament`, `election` and `auth` databases and roles from `macro-infra/docker/postgres-init/`. An **existing** volume doesn't run that, and a service fails to start without its database. So first start Postgres if it isn't running (the same compose command with `up -d postgres`), then run `docker exec -i macrohub-postgres sh -s < macro-backend/macro-infra/docker/postgres-init/01-service-databases.sh` (it can be re-run; add `-e ELECTION_DB_PASSWORD=...` or another service's variable after `-i` if you changed a password). A new database has no data until a scrape: see "Backend" below. **Keep an existing volume's `parliament` database: it is the only copy of its data.** Keep `macro_series` too: FRED serves the Dow Jones and S&P 500 for a rolling 10 years, so a re-scrape loses older days the database still has. A volume that still runs the old monolith needs the [migration guide's last version](https://github.com/KGjertsson/macro-hub/blob/584119f/docs/microservice-migration-guide.md) instead. `POSTGRES_USER` (`macrouser`) is the image's bootstrap superuser, for that script and maintenance: no service logs in with it.

**For working on the code**, run a service with `mvnw` and the frontend with Vite. Vite proxies each route to its service on `localhost` (8082 to 8086), so the start order doesn't matter:

1. **Postgres** (from repo root): `docker compose -f macro-backend/macro-infra/docker/docker-compose-dependencies.yml up -d`. It listens on `localhost:5432`. **It can't run next to the full stack's Postgres as a second one:** both Compose files define the same `postgres` service (container `macrohub-postgres`, port 5432, Compose project `docker`, volume `docker_pgdata`). With the full stack up, this command leaves its Postgres running and warns about orphan containers (ignore it, and don't pass `--remove-orphans`), and you share that database, so only stop the stack's containers that hold 8082, 8083, 8084, 8085 or 8086. If `.env` sets `REGIONAL_STATISTICS_DB_PASSWORD`, `MACRO_SERIES_DB_PASSWORD`, `PARLIAMENT_DB_PASSWORD`, `ELECTION_DB_PASSWORD`, `AUTH_DB_PASSWORD` or `MONITORING_DB_PASSWORD`, pass the same `--env-file`, or Compose re-creates the container (on the same volume). A service that is running then answers 500 for a few seconds and reconnects by itself: see "Database". Anything else on port 5432 makes it fail to start.
2. **The service you're working on** (from `macro-backend/`), see below. `-am` builds `macro-platform` with it; only the application module actually runs (`spring-boot.run.skip` in the poms).
3. **Frontend** (from `macro-frontend/`): `PATH=~/.nvm/versions/node/v22.22.1/bin:$PATH npm run dev`. Open `http://localhost:5173`.

**To work on `regional-statistics-service`** (from `macro-backend/`, with the Compose Postgres on 5432; stop the full stack's service container first if it holds 8082): `JAVA_HOME=~/.sdkman/candidates/java/current ./mvnw -pl regional-statistics-service -am spring-boot:run`. It needs no profile and no `.env`. Its base properties use `localhost:5432/regional_statistics`. For any other database, set `SPRING_DATASOURCE_URL` explicitly.

**To work on `macro-series-service`** (from `macro-backend/`, with the Compose Postgres on 5432; stop the full stack's service container first if it holds 8083): `JAVA_HOME=~/.sdkman/candidates/java/current ./mvnw -pl macro-series-service -am spring-boot:run`. It needs no profile. The working directory is `macro-series-service/`, so `.env` there is picked up, which only a Riksbanken or Fed scrape needs. Its base properties use `localhost:5432/macro_series`. For any other database, set `SPRING_DATASOURCE_URL` explicitly.

**To work on `parliament-service`** (from `macro-backend/`, with the Compose Postgres on 5432; stop the full stack's service container first if it holds 8084): `JAVA_HOME=~/.sdkman/candidates/java/current ./mvnw -pl parliament-service -am spring-boot:run`. It needs no profile and no `.env`. Its base properties use `localhost:5432/parliament`. For any other database, set `SPRING_DATASOURCE_URL` explicitly.

**To work on `election-service`** (from `macro-backend/`, with the Compose Postgres on 5432; stop the full stack's service container first if it holds 8085): `JAVA_HOME=~/.sdkman/candidates/java/current ./mvnw -pl election-service -am spring-boot:run`. It needs no profile and no `.env`. Its base properties use `localhost:5432/election`. For any other database, set `SPRING_DATASOURCE_URL` explicitly. It reads party colours from `parliament-service` on `localhost:8084` and uses Valmyndigheten's until that answers.

**To work on `auth-service`** (from `macro-backend/`, with the Compose Postgres on 5432; stop the full stack's service container first if it holds 8086): `JAVA_HOME=~/.sdkman/candidates/java/current ./mvnw -pl auth-service -am spring-boot:run`. It needs no profile and no `.env`, and writes mails to its log. Its base properties use `localhost:5432/auth`. For any other database, set `SPRING_DATASOURCE_URL` explicitly.

### Backend (from `macro-backend/`)

```bash
# Build (each application's jar is <module>/target/<module>-1.0.0.jar, with macro-platform inside)
mvn clean package

# Run all tests of all modules (not the acceptance tests, see below)
mvn test

# Run a single test class
mvn test -Dtest=MacroSeriesControllerTest

# Run a single test method
mvn test -Dtest=MacroSeriesControllerTest#shouldReturnOk_whenValidBundleRetrieved

# Generate a service's JOOQ model, from its own database at the latest migration: the command deletes the classes of
# tables it doesn't find. The profile is named after the service, so -am leaves macro-platform's model alone. The phase
# is compile, because a service can only resolve macro-platform once that has been compiled. The default is that
# service's database on the Compose Postgres, with its role. For any other database, add -Djooq.codegen.url=...
mvn -P jooq-codegen-regional-statistics compile -pl regional-statistics-service -am
mvn -P jooq-codegen-macro-series compile -pl macro-series-service -am
mvn -P jooq-codegen-parliament compile -pl parliament-service -am
mvn -P jooq-codegen-election compile -pl election-service -am
mvn -P jooq-codegen-auth compile -pl auth-service -am

# Generate macro-platform's JOOQ model (series_configuration, scrape_action_queue, flyway_schema_history). Every service's
# database has these tables; the default is localhost:5432/election with its role
mvn -P jooq-codegen-platform compile -pl macro-platform
```

```bash
# Acceptance tests: package the jars, build the :acceptance images, then run them (from anywhere; about 3 min in CI, of which the tests about 2 min)
macro-backend/macro-infra/scripts/acceptance-test.sh

# With those images built and nothing changed, only the tests (from macro-backend/)
mvn -pl acceptance-tests verify
```

A fresh database has series configs but no data points (`chart-data` returns 204). Populate everything with `MACRO_HUB_ADMIN_EMAIL=... MACRO_HUB_ADMIN_PASSWORD=... macro-backend/macro-infra/scripts/scrape-all.sh [gateway]` (default gateway `http://localhost:8081`; needs `auth-service` running, an admin account and `jq`), which logs in, enqueues everything and drains each queue, per service and in parallel. For one service, `POST .../enqueue-all` followed by `POST .../scrape-from-queue` on its paths (see the table at the top), with an admin's `Authorization: Bearer` token. On a fresh database the crons fill it too, during the 22:00 hour, without a login.

Flyway migrations run automatically on application startup via `spring-boot-starter-flyway` (Boot 4 no longer auto-configures Flyway from `flyway-core` alone; there is no Flyway Maven plugin).

### Configuration profiles

Each service has one `application.properties`, with defaults for the Compose Postgres and its own database and role, and no profiles besides `test` (`src/test/resources/application-test.properties`, a TestContainers datasource). Without `SPRING_DATASOURCE_URL`, `localhost:5432` applies, which inside a container is nothing, so Compose sets it.

- Every service sets `macro.scrape.path-prefix` (no default: it doesn't start without one), `spring.flyway.baseline-on-migrate=true`, `spring.flyway.baseline-version=0`, `spring.web.resources.add-mappings=false`, `spring.jooq.sql-dialect=POSTGRES`, the connection pool's sizes (see "Database"), and `management.endpoints.web.exposure.include=health,prometheus`, `management.metrics.tags.application` (the Compose service's name), the `http.server.requests` SLO buckets and the six tracing lines (`management.opentelemetry.enabled`, `management.tracing.export.enabled`, the sampling probability, the service name and the two exporter loggers, see "Observability")
- Riksbanken and Fed scrapes require `riksbanken.prod.subscription.key` / `fed.prod.subscription.key` (env: `RIKSBANKEN_PROD_SUBSCRIPTION_KEY`, `FED_PROD_SUBSCRIPTION_KEY`). They are `macro-series-service`'s, and only it gets them
  - Locally, put them in `macro-backend/macro-series-service/.env` (copy `.env.example`; gitignored). Spring loads it via `spring.config.import=optional:file:.env[.properties]`, relative to the working directory, which is `macro-series-service/` under `spring-boot:run` (run a jar from there too). No other service reads a `.env`
  - For `docker-compose-all.yml`, pass `--env-file macro-backend/macro-series-service/.env`. That one file also holds Compose's optional database passwords, so every service's Compose command uses it
  - `.githooks/pre-commit` rejects commits that stage `.env` files (even via `git add -f`). Enable it once per clone: `git config core.hooksPath .githooks`. The hook is opt-in, so CI's `frontend` job also fails if any `.env` file is tracked (same rule: `.env`, `.env.<anything>`, except `.env.example`)

### Frontend (from `macro-frontend/`)

```bash
npm install
npm run dev        # Vite dev server
npm run build      # production build
npm run build:dev  # development-mode build
npm run lint
npm run typecheck  # tsc --noEmit for tsconfig.app.json (src/) and tsconfig.node.json (vite.config.ts, tailwind.config.ts); vite build does not type-check
npm run preview    # serve the production build
```

- Uses Recharts for charts, TanStack Query, React Router; `@/` aliases `src/`
- Kommun/region/valkrets maps (`ChoroplethMap`) render `public/geo/kommuner.topo.json`, `lan.topo.json` and `valkretsar.topo.json` with d3-geo. They are generated from SCB's CC0 boundary shapefiles by `scripts/build-geo.sh` (run from `macro-frontend/`; needs network and `npx`), and the outputs are committed. Valkretsar are dissolved from the kommun layer via `scripts/valkretsar.csv` (kommunkod → valkrets); update it if the valkrets division changes
- DeSO/RegSO boundaries for the Områdesstatistik map are in `public/geo/deso_2018.topo.json`, `deso_2025.topo.json`, `regso_2020.topo.json` and `regso_2025.topo.json` (object name = file stem; properties `code` (desokod/regsokod without version suffix), `name` (`regsonamn`, or `"<kommunnamn> <desokod>"` for DeSO), `kommunkod`, and on DeSO also `regsokod`). They are generated from SCB's WFS (`geodata.scb.se/geoserver/stat/wfs`, CC0) by `scripts/build-geo-scb-areas.sh` (run from `macro-frontend/`; needs network, `npx` and `node`, ~2 min). The script fails if a layer's feature count differs from the WFS hit count or a code is missing/duplicated. SCB's 2025 layers extend into territorial waters, so the script clips them to the dissolved land outline of DeSO 2018 / RegSO 2020 (lakes stay inside areas in every version). Simplification is Douglas-Peucker with a tolerance scaled by area (~4 m for inner-city areas, up to 150 m for rural ones) to keep the files at ~3.0 MB (DeSO) and ~1.9 MB (RegSO); `quantization=1e6` keeps vertices within ~1.5 m for street-level zoom
- The Områdesstatistik page (`/omraden`, `src/pages/RegionalStatistics.tsx`, components in `src/components/regionalmap/`) is lazy-loaded so MapLibre GL (`maplibre-gl`, pinned exact; its worker is set via `setWorkerUrl` from a `?url` import because bundling breaks the library's own lookup) stays out of the main bundle. The basemap is OpenFreeMap's `positron` style (no API key; attribution OpenFreeMap/OpenMapTiles/OpenStreetMap comes from the style, SCB is added). The values' `geoVersion` picks which boundary file is fetched (TanStack Query, cached per version). Areas are coloured via feature-state: single-sign values in up to 9 blue classes (breaks at 1/7..5/7 and p90, p97, p99, or the mirror p1, p3, p10 and 2/7..6/7 when `median - p1 >= 1.5 * (p99 - median)` and `p1 > min`, so a long tail is not one wide class; ties can give fewer), values with both signs (e.g. flyttnetto) in 7 red–gray–blue diverging classes (3 quantile classes per side, gray around zero). Borders follow the class too: `borderColor` in `classification.ts` picks white or dark, whichever contrasts more with the fill as composited over the basemap, and `line-opacity` falls off below zoom 8 so country zoom doesn't turn grey. URL state: `l` (DeSO|RegSO), `i` (indicator id), `y` (year), `a` (area code); an indicator without DeSO data is shown at RegSO. Address search uses Photon (`photon.komoot.io`, bbox around Sweden, results filtered to `countrycode=SE`; Photon rejects `lang=sv`, so no lang is sent) and finds the containing area with d3-geo `geoContains`
- shadcn-ui components live in `src/components/ui/` (configured via `components.json`)
- Backend base URL is `rootUrl` in `src/models/Constants.ts`, set at build time by `VITE_API_URL` (trailing slash stripped). Unset or empty means same origin (relative `/macro-analyzer/...` URLs), which nginx and the Vite proxy serve. It calls `/macro-analyzer/series-config`, `/macro-analyzer/chart-data` and the parliament, election and `regional-statistics` endpoints
- The dev server listens on port 5173. `vite.config.ts` proxies `/macro-analyzer` to the backends on `localhost` (8082 to 8086), split per domain the same way as the nginx routes, and answers 404 for any other path under `/macro-analyzer/`; `vite preview` (port 4173) uses the same proxy. A `.env.development` can't set these: the pre-commit hook and CI reject it. Backend CORS still allows all origins, for a build with `VITE_API_URL` set. That URL must be a gateway (nginx or Vite), not a backend: each service only answers its own routes
- Login is `src/auth/` and the pages under `/konto/` (`logga-in`, `registrera`, `aterstall-losenord`) in `src/pages/account/`. `AuthProvider` holds the JWT in a ref, so it is gone on a reload, and `useAuth().getAccessToken()` renews it from the session cookie when needed. A `localStorage` flag says only that a session may exist, so an anonymous visit makes no `/auth/token` call. `useFragmentToken` removes a mailed link's token from the address bar. The session cookie is same-origin, so a build with `VITE_API_URL` on another origin can't log in
- Production builds send browser errors and Web Vitals to `/telemetry/collect` with Grafana Faro, from a chunk of their own: see "Observability"
- Package manager is npm; `package-lock.json` is the only lockfile (don't add `bun.lockb`/`yarn.lock`)

### Docker (from repo root)

```bash
# Dependencies only (PostgreSQL on localhost:5432, the same service as the full stack's, so not at the same time as a second one)
docker compose -f macro-backend/macro-infra/docker/docker-compose-dependencies.yml up

# Full stack (PostgreSQL + regional-statistics-service on :8082 + macro-series-service on :8083 + parliament-service on :8084 + election-service on :8085 + auth-service on :8086 (localhost only) + frontend on :8081) — build the backend images first:
#   (cd macro-backend && ./mvnw clean package && docker build -t regional-statistics-service regional-statistics-service && docker build -t macro-series-service macro-series-service && docker build -t parliament-service parliament-service && docker build -t election-service election-service && docker build -t auth-service auth-service)
# The frontend image is built by compose (add --build after frontend changes)
docker compose --env-file macro-backend/macro-series-service/.env -f macro-backend/macro-infra/docker/docker-compose-all.yml up
```

- The frontend container (`macro-frontend/Dockerfile`) builds with Node 22 and serves `dist/` with nginx on 8081; `nginx/default.conf.template` falls back to `index.html` for `BrowserRouter` routes
- The image is built with `VITE_API_URL` empty (build arg, override with `--build-arg VITE_API_URL=...`, which must be a gateway, because no single backend serves every route), so the browser calls the backend on the frontend's own origin and nginx proxies it per domain, each route with its own variable (`scheme://host:port`, no trailing slash; the defaults are the compose services):
  - `MACRO_SERIES_URL` (`http://macro-series:8083`): `/macro-analyzer/series-config`, `/macro-analyzer/chart-data`, `/macro-analyzer/scrape/macro-series/`
  - `REGIONAL_STATISTICS_URL` (`http://regional-statistics:8082`): `/macro-analyzer/regional-statistics/`, `/macro-analyzer/scrape/regional-statistics/`
  - `PARLIAMENT_URL` (`http://parliament:8084`): `/macro-analyzer/parliament/`, `/macro-analyzer/scrape/parliament/`
  - `ELECTION_URL` (`http://election:8085`): `/macro-analyzer/municipalities/`, `/macro-analyzer/regions/`, `/macro-analyzer/constituencies/`, `/macro-analyzer/scrape/election/`
  - `AUTH_URL` (`http://auth:8086`): `/macro-analyzer/auth/`. Requests are limited to 10 per minute per client address, with a burst of 10, and answer 429 beyond it, except `token`, `logout` and `jwks.json` by exact match. The limit is the route's default because a list of limited paths would miss `/login;x=1`, which Spring still routes to login
  - `FARO_URL` (`http://alloy:12347`): `/telemetry/collect`, POST only (405 otherwise), proxied to Alloy's `/collect`. Outside `/macro-analyzer/`, and see "Observability"; without Alloy it answers 502 within about a second
  - Any other path under `/macro-analyzer/`, and `/macro-analyzer` itself, answers 404 for every method. Without that it would fall through to `location /` and get `index.html` with a 200. The exception is a routed prefix without its slash, such as `/macro-analyzer/municipalities` or `/macro-analyzer/scrape/election`: nginx's automatic redirect answers those with a 301 and a relative `Location` (`absolute_redirect off`), which keeps the client's host and port, as the container's own port is 80 whatever port it is published on. The same goes for a directory of the frontend, such as `/assets` or `/geo`
- A new variable needs a default in the Dockerfile, because the entrypoint leaves an unset one as the literal `${X}`. A variable set to an empty value makes nginx exit at startup (`invalid number of arguments in "set" directive`), so write literal values in Compose rather than `${X:-}`. The proxy settings, including the 30-minute `proxy_read_timeout`, are set once on the `server` and inherited by every route
- The nginx image's envsubst entrypoint renders the template; each upstream is resolved per request with the resolver from `/etc/resolv.conf` (`NGINX_ENTRYPOINT_LOCAL_RESOLVERS=1`), so nginx starts before the backend is up. nginx's resolver ignores resolv.conf search domains, so outside compose give the variables a fully qualified name

### Observability (from repo root)

Grafana, Loki, Grafana Alloy, Prometheus, Tempo, cAdvisor and postgres_exporter run from `macro-backend/macro-infra/docker/docker-compose-observability.yml`, with their config in `observability/` next to it ([ADR 0009](docs/adrs/0009-grafana-loki-prometheus-for-local-observability.md)). They are a Compose project of their own, `macrohub-observability`, so stopping or re-creating them doesn't touch the app, and no orphan warnings appear.

```bash
DOCKER_ROOT=$(docker info -f '{{.DockerRootDir}}') docker compose -f macro-backend/macro-infra/docker/docker-compose-observability.yml up -d
```

- Open `http://localhost:3000` and log in as `admin` with `GRAFANA_ADMIN_PASSWORD` (default `grafanapassword`, read only on an empty volume). Loki, Prometheus and Tempo are provisioned as data sources. Under Explore, `{service="election"}` shows a service's logs. Prometheus is also on `http://localhost:9090`. Both ports are bound to 127.0.0.1, and Loki, Alloy, Tempo, cAdvisor and postgres_exporter publish none
- **The app stack must have been created first:** the project joins its `docker_default` network as an external network, and fails to start without it. Any `up` of `docker-compose-all.yml` or `docker-compose-dependencies.yml` creates it, and the network stays after the containers stop. Don't create it by hand, because Compose rejects a network without its labels. A `docker compose down` of the app stack leaves `docker_default` in place while the observability stack is attached to it
- `DOCKER_ROOT` is the Docker root that cAdvisor mounts, by default `/var/lib/docker`. The snap install's is `/var/snap/docker/common/var-lib-docker`; the command above reads it from the daemon
- Alloy reads the logs of the Compose project `docker` only, through the Docker socket, with the labels `service` (Compose service) and `container`. Other projects on the machine stay out of Loki. cAdvisor reports every container on the host, with the container name in the `name` label: `container_cpu_usage_seconds_total{name="macrohub-election"}`
- **Service logs are JSON under Compose:** `docker-compose-all.yml` sets `LOGGING_STRUCTURED_FORMAT_CONSOLE=ecs` and `SPRING_MAIN_BANNER_MODE=off` on each service. `mvnw spring-boot:run` and the acceptance suite don't set them, so they stay plain text, and there's no `logback.xml`, because Boot only applies structured logging to its own default configuration. Alloy parses the JSON and adds a `level` label; a logged exception is one line with `error.stack_trace` in it, which Loki's `| json` exposes as `error_stack_trace`. Plain-text lines, such as Postgres's and the nginx error log, are kept and only lack `level`. Under Compose every line written during a traced request also has `traceId` and `spanId`, see "Traces". A multi-line stage folds a Java stack trace that didn't go through the logger, such as an uncaught exception on stderr, into one entry
- **The gateway's access log is JSON too** (`json_access` in `nginx/default.conf.template`): `time`, `level` (from the status: 5xx `error`, 4xx `warn`, else `info`), `method`, `uri`, `route`, `status`, `bytes`, `request_time`, `upstream_response_time`, `upstream_status`, `trace_id` (see "Traces"). `level` and `route` are Loki labels. `route` is a closed set, one per routed prefix (`parliament`, `scrape-election`, `unknown-api`, `frontend`), from a `map` on `$uri`, so a new route in the template needs a line there
- **Metrics:** each service exposes only `health` and `prometheus` under `/actuator` on its own port, and every series has an `application` label with the Compose service's name, matching the logs' `service` label. Prometheus scrapes them by Compose name as the job `services`, with JVM, `http_server_requests_seconds` (with `uri` as the route's template, and SLO buckets rather than a percentiles histogram), `hikaricp_connections_*` and `macro_scrape_*` series. Those ports are published on the host as before, so `/actuator/prometheus` answers there; through the gateway it is not an API path and gets the frontend's `index.html` like any other unknown page
- **Scrape metrics** come from `ScrapeService` through `ScrapeMetricsPort`, which `ScrapeMetricsMicrometerAdaptor` implements. No label holds a series name; the failing item's name is in the log line `Scrape item failed: name=... flow=...`, which every `FAILED` item logs. `macro_scrape_items_total{flow,result}` counts processed items, `result` being `success` (also a `ScrapeResult.EMPTY`: nothing new to write) or `failed`, with a `flow` of `unknown` for an item without a config. `macro_scrape_item_duration_seconds` per `flow` has SLO buckets from 500 ms to 30 min. `macro_scrape_queue_pending` is the queue's `status = 0` rows, read from the database at most every 30 seconds whatever Prometheus asks, and `NaN` after a failed read, which is remembered for those 30 seconds too, so during a Postgres outage a metrics scrape waits out the 5-second `connection-timeout` at most once per interval and reports no stale count. `macro_scrape_last_success_timestamp_seconds` per `flow` is held in memory because the queue doesn't record when an item was done, so it has no series before a flow's first success after a start: the Scrapes dashboard shows it with `last_over_time`, and no alert depends on it. The counter and timer of every registered flow start at 0, or Prometheus would see no increase for the first failure. Recording never fails a scrape: `ScrapeService` catches any `RuntimeException` from the port
- **Postgres metrics** come from postgres_exporter, which connects to the Compose Postgres by its service name on `docker_default` and is scraped as the job `postgres`. It logs in as the role `monitoring` (`pg_monitor`), created by `postgres-init/02-monitoring-role.sh`: that role may connect to the `postgres` database only, from where `pg_stat_database` and `pg_locks` show every database, so it can't read a table of a service. Its password is `MONITORING_DB_PASSWORD` (default `monitoringpassword`), which must not contain a space: the exporter then reports `pg_up 0` with a malformed DSN, so `Postgres down` fires while the other series keep arriving. If you set it in `.env`, also pass `--env-file macro-backend/macro-series-service/.env` to the command above. **An existing volume doesn't run init scripts, so it needs the role created once**, with the app's Postgres running (it can be re-run, and picks up a changed password; add `-e MONITORING_DB_PASSWORD=...` after `-i` if you changed it): `docker exec -i macrohub-postgres sh -s < macro-backend/macro-infra/docker/postgres-init/02-monitoring-role.sh`. Until then the exporter runs, its target is `up`, it reports `pg_up 0` and no Postgres statistics, Postgres logs `password authentication failed for user "monitoring"` twice per scrape (every 15 seconds), the Postgres dashboard shows `No data` and `Postgres down` fires if a service is running. The exporter connects on the next scrape after the command, without a restart
- **Dashboards** are provisioned from `observability/dashboards/*.json` into the folder `macro-hub`, and read-only in Grafana: `Macro Hub Containers`, `Macro Hub Services`, `Macro Hub Gateway`, `Macro Hub Postgres` (connections per database against `max_connections`, sizes, committed and rolled back transactions, cache hit ratio, deadlocks, locks and the longest running transaction, for the service databases), `Macro Hub Browser` (see "Browser telemetry"), `Macro Hub Scrapes` (results, failure share, durations, pending items, time since last success, the alerts' states, and the failed items' log lines, with a link from the failures panel to the Logs dashboard), `Macro Hub Load Tests` (see "Load tests") and `Macro Hub Logs` (service and level filters, plus a text search; each line shows only the time and Grafana's level column, which comes from the `level` label, then the service and the message from `line_format`, and expanding it shows the other fields, including the stack trace and, in `full_json`, the original line). `Macro Hub Browser` has the error count and rate, top messages, recent errors with their stacks, Web Vitals at p75 coloured by their good and poor limits, and a per-page table. They are plain Grafana JSON; change one by editing the file. Grafana picks it up within 10 seconds, and a panel with no matching series shows `No data` (the 5xx panels, normally)
- **Alerts** are Grafana-managed rules, provisioned from `observability/alerting/rules.yml` into the folder `macro-hub`, and shown only in Grafana's Alerting page and on the Scrapes and Postgres dashboards: there is no contact point, and Grafana 13's default policy routes to its built-in `empty` receiver, which has no integrations, so nothing is sent and nothing is logged about sending. Rules evaluate every minute. `Service down` (3 min, only while another service is still up, so a stopped stack isn't five alerts), `Scrape items failing persistently` (failures in at least 4 of the last 6 ten-minute windows, so a one-minute source outage doesn't fire), `Scrape queue not draining` (items pending and none processed, also a failed one, for at least 45 min, beyond the longest single item), `Connection pool saturated` (5 min at the maximum of 8), `Gateway 5xx responses` (over 10 per 5 min per route, from Loki, sustained for 5 min, without the `telemetry` route, whose 502s only mean that the optional Alloy is down), `Postgres down` (3 min, only while a service is still up, also when the exporter can't log in), `Postgres connections near maximum` (over 80 of the 100 for 5 min), `JVM heap near its maximum` (over 92% for 15 min, longer than a first SCB scrape holds its values) and `Container restarting repeatedly` (at least 3 restarts in 30 min). Every query returns nothing or 0 while its condition isn't met, so No Data means healthy: a stopped service, a service that has never scraped or a stopped stack produces no alerts by itself. Evaluation errors, such as a Prometheus restart, keep the last state. Unlike the dashboards, Grafana only reads the rules file when it starts, so a change needs a restart of the `grafana` container
- **Browser telemetry** comes from Grafana Faro (`@grafana/faro-web-sdk`, pinned exact), started in `src/main.tsx` only in production builds and from a dynamic import of `src/telemetry/browserTelemetry.ts`, so it is a chunk of its own, outside the main bundle. It sends uncaught errors, unhandled promise rejections and Web Vitals (LCP, INP, CLS, FCP, TTFB) to `/telemetry/collect` on the page's own origin, and nginx proxies that to Alloy's `faro.receiver` (port 12347, on `docker_default`, not published). It sends no session id, user, `console` output, request or response bodies, traces or session replay, and a page's query string is removed before sending, because it holds what the visitor picked. Every item carries the page's path, the app's name and environment, the SDK's name and version, and the browser's name, version, brands, user agent, language, viewport, mobile flag and OS name and version. A Web Vital also has its attribution timings (such as `element_render_delay` and `interaction_time`), its rating, the navigation type and the CSS selector of the element involved (`context_element`, `context_interaction_target`, `context_largest_shift_target`). Stack traces stay minified: source maps aren't uploaded, and `sourcemaps { download = false }` keeps the receiver from fetching them, because by default it fetches every frame's URL, which the client chooses, from inside `docker_default`. Loki's labels are `service="browser"`, `kind` (`exception`, `measurement`) and, for exceptions, `level="error"`; the rest is in the JSON line (`| json`: `value`, `stacktrace`, `page_url`, `value_lcp`...), so a new label must stay a closed set. The receiver takes 10 requests per second with a burst of 30 and answers 429 beyond it, because the gateway's port 8081 is published on all interfaces; nginx and the receiver both refuse a body over 256 KiB
- **Telemetry fails silently while the observability stack is down.** The SDK's default transport tries a 502 or network error three times per batch and writes `console.error` when it gives up, so `browserTelemetry.ts` sets one attempt and turns the SDK's logger off. A failed batch is dropped: nothing is shown or stored, and the app works as before. What stays is the browser's own `Failed to load resource` line for each failed POST, a few per page load, which no code can suppress. Docker's DNS takes seconds to give up on a stopped container's name, so the route has a `resolver_timeout` of 1 s. `vite preview` has no such route and answers the POST with a 404, and under `npm run dev` nothing is started. A build with `VITE_API_URL` set still posts to its own origin
- **Traces** go from each service to Tempo with OTLP over HTTP, when `docker-compose-all.yml` sets `MANAGEMENT_OPENTELEMETRY_ENABLED`, `MANAGEMENT_TRACING_EXPORT_ENABLED` and `MANAGEMENT_OPENTELEMETRY_TRACING_EXPORT_OTLP_ENDPOINT` (`http://tempo:4318/v1/traces`). Each service's `application.properties` sets the first two to `false`, so under `mvnw spring-boot:run`, the tests and the acceptance suite nothing is exported and an incoming `traceparent` isn't read. Spans are still created there, because Boot builds an SDK without a span processor and the tracing observation handlers, `UntracedObservationHandler` included, run regardless of the switch, but they are dropped at once. The MDC holds `traceId` and `spanId`, and `logging.expect-correlation-id`, which follows `management.tracing.export.enabled`, keeps them out of the plain-text lines. The dependencies are in `macro-platform`, Boot's OpenTelemetry modules rather than `spring-boot-starter-opentelemetry`, because that also pulls in the OTLP metrics registry. A span's `service.name` is the Compose service's name (`management.opentelemetry.resource-attributes[service.name]`), the same value as the metrics' `application` label and Loki's `service` label. Sampling is 100% (`management.tracing.sampling.probability`). The propagation format is W3C `traceparent`
  - **What makes a span:** `http.server.requests` and `http.client.requests` observations, and the SQL statements of a traced request. The observations are an incoming HTTP request and `ParliamentPartiesClient`'s call (the only `RestClient` in the backend, built from Boot's instrumented `RestClient.Builder`, so its one fetch per refresh interval, or per 15-second retry until a first list has loaded, is one trace across election and parliament). `UntracedObservationHandler` (`shared/config/`, ordered first of the tracing handlers) takes every `/actuator` request and `@Scheduled` run, so neither the 15-second Prometheus scrape nor a cron drain is a trace. Their metrics stay: `TracingAwareMeterObservationHandler` throws in `onStop` if no handler has set a `TracingContext`, which is why that handler sets one rather than the other tracing handlers merely skipping the context. `QuerySpanListener` (`shared/config/`, a jOOQ `ExecuteListener`) adds a child span per statement, named like `select riksdag_party`, covering connection wait, execution and fetch, with `db.system.name` and `db.query.text`, the SQL with `?` for its bind values. A failed statement's span is an error and holds only the exception's class, because its message can repeat a bound value (`Key (email)=(...) already exists`). It only does so inside a trace, so a cron run's queries are no spans and no traces of their own, and not under `/macro-analyzer/scrape/`, because a scrape can run far more statements than a trace can usefully show. A scrape's calls to its sources use `HttpURLConnection`, so a full SCB scrape adds no spans of its own: a manual drain is one span for the request, a cron drain none. Flyway doesn't go through jOOQ, and BEGIN and COMMIT aren't statements of jOOQ's, so neither is a span
  - **The gateway makes no span:** the stock nginx image has no OpenTelemetry module. It sends upstream `traceparent: 00-$request_id-<the first 16 hex characters of $request_id>-01` on every proxied route, and always replaces what a client sent, so that the port 8081, published on all interfaces, can't be used to set trace ids or switch sampling. `tracestate` and `baggage` are cleared. The access log's `trace_id` is `$request_id` on proxied routes and empty on `frontend`, `telemetry` and `unknown-api` routes, so a line only offers a trace link where a trace can exist. Because the parent span id names a span that was never exported, Tempo reports these traces as `<root span not yet received>` and the service's span has no parent in view; the trace is complete apart from that. `trace_id` and the service logs' `traceId` are never Loki labels: Alloy parses them only for `level` and `route`
  - **Grafana:** a service's JSON log line has `traceId` and `spanId` at the top level. Loki's derived fields link a raw line's `traceId` or the gateway's `trace_id` (regex) and the `traceId` or `trace_id` of a `| json` query (the Logs dashboard's line format drops the raw line) to Tempo. Grafana only reads the data sources when it starts, so a change to them needs a restart of the `grafana` container. From a trace, Tempo's trace-to-logs runs `{service=~".+"} |= "<trace id>"` over the span's time ±1 min, which finds the gateway's access line and every service's lines. `Macro Hub Gateway` has an access-log panel of the service routes, and `Macro Hub Logs`'s details link the same way. Prometheus stores exemplars (`--enable-feature=exemplar-storage`), and `HTTP latency p95 per route` on `Macro Hub Services` shows them with a link to the trace. Open Explore with the Tempo data source for `{ resource.service.name="election" }` and the like
  - **Tempo being down costs nothing:** export runs on the OpenTelemetry batch thread, spans wait in a queue of at most 2048 and are then dropped, and the exporter's two warnings (`io.opentelemetry.exporter.internal.http.HttpExporter` and the queue-full line of `...sdk.trace.export.BatchSpanProcessor`) are turned off in `application.properties`, so a stack that is down, or Tempo not started, adds no latency and no log lines. Tempo runs from `observability/tempo.yml`, 7 days' retention on its own volume, and accepts OTLP on `tempo:4318` only, inside `docker_default`
- Prometheus runs with `--web.enable-remote-write-receiver`, only so the load test's k6 can push to it (see "Load tests"). It has no other sender and no authentication, so it relies on the port being bound to 127.0.0.1
- Retention is 30 days in Loki, 30 days or 5 GB in Prometheus, and 7 days in Tempo. `docker compose -f ... down -v` on this file only removes this project's volumes, and none of them is `docker_pgdata`

### Load tests (from repo root)

`macro-backend/macro-infra/scripts/load-test.sh [--allow-remote] [smoke|load|stress] [gateway]` runs [k6](https://k6.io) from the pinned `grafana/k6` image against the endpoints our own frontend calls, through the gateway, so nginx is part of what is measured. It starts nothing and adds nothing to the stack, nothing else starts it, and it isn't in CI or the acceptance suite. The k6 scripts are in `macro-backend/macro-infra/load-tests/`. **It only reads, but it is real load on your real local stack, so pick the profile deliberately:** run it when nothing important is running. The numbers are about the machine and the data of that moment, not the application alone: k6 and the stack share the CPU, and a scrape running at the same time skews them, so check that no scrape is running first. They are only worth comparing with a populated database, because `chart-data` and `regional-statistics/values` answer 204 quickly on an empty one.

- **Profiles:**

```bash
macro-backend/macro-infra/scripts/load-test.sh smoke    # every page in turn, 3 rounds, 1 user, a few seconds: does it work
macro-backend/macro-infra/scripts/load-test.sh load     # 5 page views per second for 5 minutes (about 15 requests/s)
macro-backend/macro-infra/scripts/load-test.sh stress   # doubles from 10 to 160 page views per second over about 7.5 minutes, stops itself when a group's errors pass 10%
```

  `smoke` is the default. `load` is a rate this one host should hold comfortably, and far more than real use; its thresholds (p95 per endpoint group under 1 s, errors under 1%) are starting values to tune once real numbers exist. `stress` is the same mix on an open arrival rate, so overload shows up as latency and `dropped_iterations` rather than as a slower run; it stops itself once a group's errors pass 10%, and a run that finishes the ramp can still fail on its p95 limit of 5 s per group. Change them with `LOAD_TEST_RATE`, `LOAD_TEST_DURATION` (k6 duration), `LOAD_TEST_MAX_VUS`, `LOAD_TEST_STRESS_MAX_RATE`, `LOAD_TEST_STRESS_STEP_SECONDS`, `LOAD_TEST_SMOKE_ROUNDS`, `LOAD_TEST_P95_MS` and `LOAD_TEST_ERROR_RATE`.
- **Target:** the default gateway is `http://macro-frontend` on `docker_default`, the Compose gateway. `http://localhost:<port>` also works, with host networking, which is also how to load Vite (`http://localhost:5173`). Any other host needs `--allow-remote` as the first argument, so a run can't load something remote by accident. The URL must be `http[s]://host[:port]`, nothing else
- **What it requests:** every backend endpoint the frontend calls, read from `macro-frontend/src`: `series-config`, `chart-data`, `/parliament/{parties,elections,composition,members,members/{id}}`, the `elections` list and `{code}` detail of `municipalities`, `regions` and `constituencies`, and `/regional-statistics/{indicators,values}`. A page view (`pages.js`) makes the calls the real page makes, and the mix (`weight` in `pages.js`) is a guess: 30% start page, 15% chart, 15% Riksdag, 10% each politician, kommun and områden, 5% each region and valkrets. Not covered, on purpose: anything under `/macro-analyzer/scrape/` (the one function that sends requests, `send` in `gateway.js`, stops the run if a path has a `scrape` segment or is outside `/macro-analyzer/`, also encoded), `/telemetry/collect` and third parties (Photon), and static files (`index.html`, the assets, `/geo/*.topo.json`), which nginx serves without a backend
- **Values** (series names, election years, member ids, area codes, indicators and their years) are discovered at the start from the same endpoints, in `setup()`. On a stack with no data the run still works and warns at start and end which endpoints gave nothing and that the numbers don't say much (run `scrape-all.sh`); it is not a failure. A gateway that can't be reached or a service that answers anything else at discovery stops the run at once with a message naming it, so a broken stack is reported and not measured
- **Results:** k6 prints the end-of-test summary. Its `http_req_duration`, `http_req_failed` and `http_reqs` lines per `endpoint_group` (the same values as the gateway's `route` label) are what to read, and the thresholds show why a run passes or fails. The exit code is `0` on a pass, `99` when a threshold was crossed, which includes `stress` stopping itself, and `108` when the script aborted the run (a gateway it can't reach, a service failing during discovery, or a refused path)
- **In Grafana:** when the script finds Prometheus's remote-write receiver on `127.0.0.1:9090` it says so at the start and k6 also writes there, on the `macro-frontend`/`docker_default` route as `prometheus:9090`. Without it, or with a Prometheus started before this flag was added (then `docker compose -f macro-backend/macro-infra/docker/docker-compose-observability.yml up -d --no-deps prometheus` re-creates it; `--no-deps` keeps Compose from re-creating cAdvisor without `DOCKER_ROOT`), the run still completes and prints its summary. `Macro Hub Load Tests` has requests, failed share and p95/p50 latency per `endpoint_group`, p95 per endpoint, page views and dropped ones, and VUs, so set the same time range there and on the Containers, Services and Postgres dashboards to compare a run. `smoke` is over too quickly to show much on it. Discovery's requests are tagged `endpoint_group="discovery"` and left out. Labels are `name` (the URL template, never a real area code), `endpoint_group`, `method`, `status`, `scenario`, `expected_response` and `check`, and a run makes about 240 series. Latency is a native histogram (`K6_FEATURES=native-histograms`), because k6's Trend statistics are over the whole run and can't show a stress ramp's knee
- A heavy run can fire Grafana's `Connection pool saturated` and fills Loki and Tempo with its requests, because the gateway logs every one and every service traces every one (100% sampling, see "Traces").
- Snap's `docker` can't see `/tmp` but mounts from `$HOME` as usual, so the checkout must be under `$HOME`, like for the acceptance test script

Docker Compose is the only way to run the app. There is no Kubernetes deployment: [ADR 0007](docs/adrs/0007-remove-the-kubernetes-deployment-until-its-needed.md) says why, and holds the findings worth keeping.

## Architecture

The backend is five services and one library, split by domain, plus the `acceptance-tests` module, which holds no production code. Inside each module it follows **Hexagonal Architecture (Ports & Adapters)** with **Domain-Driven Design**. Every class lives in a module under `com.kg.macroanalyzer`, except the application classes in the root package and the generated jOOQ models. The Maven modules map onto the packages: `scrape`, `shared` and their jOOQ model are built in `macro-platform`, `regionalstatistics` in `regional-statistics-service`, `macroseries` in `macro-series-service`, `parliament` in `parliament-service` and `election` in `election-service`. Each application class is in `com.kg.macroanalyzer`, so its component scanning finds `macro-platform`'s beans. [`macro-backend/ARCHITECTURE.md`](macro-backend/ARCHITECTURE.md) has more diagrams.

[`docs/architecture.md`](docs/architecture.md) is a diagram of the components that run.

```
  REST ──→ adaptors.http ──→ port.in ──→ service ──→ port.out ←── adaptors.postgres ──→ PostgreSQL
                                           │
                                           └──→ domain

  InsertionAdaptor, CronEnqueueAdaptor, CronScrapeAdaptor ──→ InPort ──→ EnqueueService ──→ ScrapeQueuePort
                                                                    └──→ ScrapeService
  ScrapeService ──→ RegisteredScrapeFlow (picked by the config's scrape_flow id, built in each module's adaptors.config)
      Preparer ──→ ExistingFinder ──→ Scraper ──→ WebPort ←── adaptors.web ──→ external API
                                      Persister ──→ port.out, then ScrapeQueuePort.markAsDone

  election ──→ PartyColorPort ←── adaptors.web ──→ GET /macro-analyzer/parliament/parties (cached, refreshed in the background)
```

### Package structure (`com.kg.macroanalyzer`)

The backend is organised by domain. Every module (`scrape`, `macroseries`, `regionalstatistics`, `parliament`, `election`) uses `domain/`, `application/port/in/`, `application/port/out/`, `application/service/` and `adaptors/{http,postgres,web,config,cron}/` (`scrape` also `adaptors/metrics/`); besides them there is only `shared/`, the generated jOOQ models and the application class in the root package.

- **`scrape/`** (Maven module `macro-platform`) — the scrape core, independent of the data sources:
  - `domain/` — `ScrapeQueueItem`, `ScrapeResult`, `SeriesConfig` (every scrape flow's config, including the `scrapeFlow` id that routes it)
  - `application/port/in/` — `InPort` (enqueue, enqueue-all, scrape-from-queue) and its `ScrapeRun` result; `application/port/out/` — `ScrapeQueuePort` (queue reads/writes, `markAsDone`), `SeriesConfigPort` and `ScrapeMetricsPort`
  - `application/service/` — `InPortImpl`, `ScrapeService`, `EnqueueService`, and in `scrapeflow/` the `ScrapeFlow` pipeline (`Preparer` → `ExistingFinder` → `Scraper` → `Persister`) and `RegisteredScrapeFlow` (see below)
  - `adaptors/http/` — `InsertionAdaptor` (enqueue/scrape endpoints); `adaptors/cron/` — `CronScrapeAdaptor` drains the queue every 60s, `CronEnqueueAdaptor` enqueues all series every minute during the 22:00 hour; `adaptors/postgres/` — queue and series-config repositories; `adaptors/metrics/` — `ScrapeMetricsMicrometerAdaptor` (see "Observability"); `adaptors/config/` — preparer, series-config list and scheduler beans
- **`macroseries/`** (Maven module `macro-series-service`, with its own jOOQ model in `macroseries.jooq.generated`) — chart time series (Riksbanken, Fed and Eurostat rates, bonds, bills, exchange rates and key figures):
  - `domain/` — `MacroSeries`, `MacroPoint`, `AlignedBundle`, `InvalidBundleDimensionException`, `MacroSeriesScrapeFlows` (the `MACRO_POINT` flow id)
  - `application/port/in/` — `MacroSeriesQueries` (aligned chart data, chart series configs) and its DTOs (`BuildChartDataParams` with the `Strategy` and `TimeFrame` enums, `ChartSeriesParam`, `ChartData`, `ChartDataWithLabels`); `application/port/out/` — `MacroSeriesRepositoryPort` and the scrape payload `ConfigWithMacroPoints`
  - `application/service/` — `MacroSeriesService` (the chart list is the configs of the `MACRO_POINT` flow), in `bundleformat/` the pure calculations `TimeFilter`, `Alignment` and `LabelPadding` and the sample and time-filter strategies, and in `scrape/` `ExistingMacroPointFinder`, `MacroPointScraper` and `MacroPointPersister`
  - `adaptors/http/` — `MacroSeriesController` (`/series-config`, `/chart-data`), `SeriesConfigResponse` (a `/series-config` entry, without `scrapeFlow`) and `ColorSelectionStrategy`; `adaptors/postgres/` — `MacroSeriesPostgresAdaptor`, the per-table rate, bond, bill, exchange-rate, Fed and Eurostat repositories, and `MacroPointUpsert`, which all their writers use; `adaptors/web/` — `MacroPointWebAdaptor` and `MacroPointAdaptorFlowFactory`, which routes to the Riksbanken, Fed or Eurostat connection builder and response parser; `adaptors/config/` — the web adaptor bean (with the Riksbanken/Fed subscription keys) and the scrape flow
- **`regionalstatistics/`** (Maven module `regional-statistics-service`, with its own jOOQ model in `regionalstatistics.jooq.generated`) — SCB DeSO/RegSO statistics:
  - `domain/` — `GeoVersion`, `ScbLevel`, `ScbIndicator`, `ScbValues` and the other SCB value types, `RegionalStatisticsScrapeFlows` (the `SCB_REGIONAL` flow id)
  - `application/port/in/` — `RegionalStatisticsQueries` (indicators and values) and its DTOs; `application/port/out/` — `RegionalStatisticsRepositoryPort`, the scrape payload `ConfigWithScbIndicators` and the SCB web requests
  - `application/service/` — `RegionalStatisticsService`, and in `scrape/` the scrape flow (`ExistingScbTableFinder`, `ScbRegionalScraper`, `ScbRegionalPersister`)

The tables are selected in each module's codegen profile

### Layers inside a module

- `domain/` — records and enums of the domain (Lombok only, no Spring).
- `application/port/in/` — what the module offers: query interfaces (`*Queries`, `InPort`) and their DTOs/parameters.
- `application/port/out/` — what the module needs: repository ports (`*RepositoryPort`) and the request/config-with-data records its scrapers pass around.
- `application/service/` — implementations of the in-ports; `application/service/scrape/` holds the module's `ExistingFinder`/`Scraper`/`Persister`. `@Service` is for in-port implementations and code with dependencies. Code with no state, configuration, I/O or AOP is a `final` class with static methods, like `Alignment` or `LabelPadding`.
- `adaptors/http/` (controllers), `adaptors/postgres/` (`*PostgresAdaptor` implementing the repository port, plus jOOQ repositories), `adaptors/web/` (`WebPort` implementations, connection builders, response parsers), `adaptors/config/` (`*WebAdaptorConfiguration` for the `WebPort` beans, `*ScrapeFlowConfiguration` for the scrape flow), `adaptors/cron/` (scrape only).

### How a scrape flow plugs in

Each domain's `*ScrapeFlowConfiguration` builds a `ScrapeFlow` from the shared `Preparer` and its own finder, scraper and persister, and registers it as a `RegisteredScrapeFlow` bean under a flow id. The ids are plain strings that each module owns as constants in its `domain/` (`MacroSeriesScrapeFlows.MACRO_POINT`, `ParliamentScrapeFlows.MEMBER_OF_PARLIAMENT`/`MEMBER_ACTIVITY`, `ElectionScrapeFlows.LOCAL_ELECTION`, `RegionalStatisticsScrapeFlows.SCB_REGIONAL`); `scrape` never names them, except that `ScrapeMetricsPort.UNKNOWN_FLOW` labels items without a flow. Every `series_configuration` row says which flow scrapes it in `scrape_flow` (NOT NULL, V31). `ScrapeService` routes a queue item by name → `SeriesConfig` (through the `SeriesConfigPreparer`) → `scrapeFlow` → flow; an item whose name matches no config is `FAILED` with a warning and stays pending. At startup it fails if two flows share an id or a config's `scrapeFlow` has no registered flow (the message names the config and the id), and only warns for a registered flow that no config uses. The configs are read once at startup, so a new row needs a restart. Persisters write through their module's repository port and then call `ScrapeQueuePort.markAsDone` (with nothing to write they only mark it done). The two don't share a transaction. An item that throws is `FAILED`, doesn't stop the others and stays pending, so the cron retries it about once a minute, re-fetching from the source. The election flow can also write what it got and still leave its item `FAILED` and pending: see "Kommun, region and Riksdag elections".

### Dependency rules (`ArchitectureTest`)

Every Maven module except `acceptance-tests`, which has no production code, has its own `src/test/java/com/kg/macroanalyzer/ArchitectureTest.java` (ArchUnit, part of `mvn test`).

`macro-platform`'s enforces:

- every class resides in `scrape`, `shared` or `platform.jooq.generated`;
- `shared` depends on no module (only on itself and the platform's jOOQ model), and `scrape` only on itself, `shared` and that model;
- `scrape`'s `domain` and `application` do not depend on its `adaptors`, and no `application.port` depends on an `application.service`.

Each service's enforces the same layers for its one domain module, on top of that:

- every class except its application class resides in its module, `scrape`, `shared` or `platform.jooq.generated`;
- the module only depends on itself, `scrape` and `shared`, and `macro-platform` doesn't depend on it. `platform.jooq.generated` isn't among those, so a module can't use the queue and config tables directly;
- only its `adaptors.postgres` use its jOOQ model.

Every one of them also requires every field to be `final`, outside Lombok's builders and a short allowlist in that test (`RefreshingPartyColorAdaptor.colors`, `ScbRateLimiter.lastCallMs`); see "Immutability".

### Immutability

Values don't change once built. Domain types, DTOs and scrape payloads are records, changed with `toBuilder()`, which returns a new one; there is no `@Data`, `@Setter` or `@With`. A record with a `List`, `Set` or `Map` component copies it in a compact constructor with `ImmutableCopies` (`shared/collection/`), not `List.copyOf`/`Map.copyOf`: those reject nulls, which parsed sources and SCB's suppressed cells hold, and `Map.copyOf` loses the iteration order the JSON answers and JSON-stat's dimensions depend on. A null collection stays null. A method may fill a collection of its own, but returns it unmodifiable. `ScbValues`, `ScbRegionalScraper` and the `ScbTableValues` record wrap with `Collections.unmodifiableMap` instead of copying, because a full SCB scrape passes about 2.4 M values through them. The allowlist above is the state that has to change: the rate limiter's timestamp and the party-colour cache, which swaps a whole immutable map. `CachedMembers`' list (an `AtomicReference`), `ScrapeService`'s lock and `ScrapeMetricsMicrometerAdaptor`'s cached pending count (`pendingReading`, an `AtomicReference`) and last-success times (`lastSuccessMillis`, a `ConcurrentHashMap` of `AtomicLong`s) also change, but are `final` fields, so the rule doesn't need to list them. The `immutable-java` skill (`.claude/skills/immutable-java/`) has the detailed rules and `check.py`, which checks the records' compact constructors and what ArchUnit can't see.

Maven keeps the services' code apart: no service depends on another. The one runtime link is over HTTP: election reads the parliament service's party list (see "Kommun, region and Riksdag elections").

### Adding a new domain

A new domain is a new service. Follow [`docs/adding-a-service.md`](docs/adding-a-service.md) for the module, database, role, port, gateway route, Compose service and tests, with `parliament-service` or `election-service` as the template. Inside the module:

1. Create `com.kg.macroanalyzer.<module>` with `domain/`, `application/port/in/`, `application/port/out/`, `application/service/` (and `service/scrape/`) and `adaptors/`, and an application class in `com.kg.macroanalyzer` so component scanning also finds `macro-platform`'s beans.
2. Define the in-port (`*Queries`) and out-port (`*RepositoryPort`); implement them in a service and a `*PostgresAdaptor`.
3. Add a controller in `adaptors/http/` that only uses the in-port.
4. Add a `*WebAdaptorConfiguration` for the `WebPort` beans and a `*ScrapeFlowConfiguration` that registers a `RegisteredScrapeFlow` under a new flow id.
5. Define that flow id as a constant in the module's `domain/` (e.g. `<Module>ScrapeFlows`). `/series-config` only lists the `macro_series` database's configs, so a new flow stays out of the chart picker.
6. Set `macro.scrape.path-prefix` (a service without it doesn't start), `spring.flyway.baseline-on-migrate=true`, `spring.flyway.baseline-version=0`, `spring.web.resources.add-mappings=false`, `spring.jooq.sql-dialect=POSTGRES`, `auth.jwks-uri` (a service without it doesn't start) and the three `spring.datasource.hikari.*` lines (see "Database") and the `management.*` and tracing lines (see "Observability") in its `application.properties`, and give it its own `ArchitectureTest` and copies of `ConnectionPoolIntegrationTest`, `ActuatorExposureHttpTest` and `TracingHttpTest`. Without the `hikari` lines it still starts, on Hikari's default of 10 connections, all kept open, so count it when adding up `max_connections`.
7. Add a Flyway `V1` with the module's tables and its `series_configuration` row, then generate its jOOQ model. The row needs a `scrape_url`, a `category` and its `scrape_flow` (the id from step 5); startup fails if no flow is registered under that id.

### REST API Endpoints

- `GET /macro-analyzer/series-config` — on `macro-series-service`: list the chart series configurations, in `id` (seed) order
- `POST /macro-analyzer/chart-data` — on `macro-series-service`: retrieve aligned chart data (400 when `strategy`, `timeFrame` or `chartSeriesParams` is missing)
- `POST /macro-analyzer/scrape/{regional-statistics,macro-series,parliament,election}/enqueue?name={series}` — on that service: enqueue one of its series for scraping (202; a name it doesn't know also answers 202 and does nothing). All scrape paths need an `ADMIN` JWT: 401 without a valid one, 403 for another role
- `POST /macro-analyzer/scrape/{service}/enqueue-all` — enqueue all of that service's series (202)
- `POST /macro-analyzer/scrape/{service}/scrape-from-queue` — execute that service's pending scrapes (200, 409 while one is running)
- Any other path under `/macro-analyzer/` answers 404 on the gateway, for every method, except under a scrape prefix, where the service's security answers first: 401 without a valid token, 400 for a path with `;` (a routed prefix without its slash gets nginx's 301 to the slash, a relative `Location` that keeps the client's host and port)
- `GET /macro-analyzer/parliament/elections` — on `parliament-service`, as are the other `/parliament/*` endpoints: official seat results per election (newest first), the parties in the order V, S, MP, C, L, M, KD, SD, then any others by seats, which the Riksdag page's seat chart follows from left to right
- `GET /macro-analyzer/parliament/composition` — live seats per party from currently serving MPs, in the same party order
- `GET /macro-analyzer/parliament/parties` — party names, colours, ideology
- `GET /macro-analyzer/parliament/members?year={electionYear}` — members who sat in that term (default: latest)
- `GET /macro-analyzer/parliament/members/{intressentId}` — member detail (assignments, biography, contact, votes, speeches, motions)
- `GET /macro-analyzer/municipalities/elections?year=` / `GET /macro-analyzer/regions/elections?year=` / `GET /macro-analyzer/constituencies/elections?year=` — per kommun/region/Riksdag valkrets: seats, turnout, votes and seats per party (default: latest year)
- `GET /macro-analyzer/municipalities/{kommunkod}` / `GET /macro-analyzer/regions/{länskod}` / `GET /macro-analyzer/constituencies/{valkretskod}` — the same plus elected members and curated governance (none for valkretsar)
- `GET /macro-analyzer/regional-statistics/indicators` — SCB indicators with `availability` per level (`DeSO`, `RegSO`): years (newest first) and the boundary version (`geoVersion`) of each
- `GET /macro-analyzer/regional-statistics/values?indicator=&level=DeSO|RegSO&year=` — `{indicator, level, year, geoVersion, values: {areaCode: value}}` (default: latest year; 204 without data, 400 for an unknown level)

### Riksdagen (parliament) data

- All of this runs in `parliament-service`, on its own database and scrape lock. `MembersOfParliament` scrape upserts every person from `data.riksdagen.se/personlista` (JSONB, keyed on `intressent_id`); `MembersOfParliamentActivity` then fetches voting totals, speeches and motions per member of the latest two terms (584 members today, about 9 min with the members' scrape, throttled)
- Election seat counts are curated in `riksdag_election_result` (Flyway seed from Valmyndigheten) because Riksdagen only stores each person's *current* party. Add a new election as a migration in `parliament-service` (rows in `riksdag_election` + `riksdag_election_result`). `/parliament/parties` has no `ORDER BY`, so it answers in the table's order, which the baseline keeps as it was before the split (SD last). So a migration that changes parties updates every row in one statement, as `V2` does for the colours (from Wikipedia's `Mall:Partifärg`), or the rows it touches move to the end
- `CachedMembers` holds every member, parsed, in memory from the first read, because parsing them takes about half a second. `/parliament/members` and the activity scrape read it. A members scrape clears it, whether or not its write succeeded, and the next read loads it again. A change to `swedish_members_of_parliament` by any other route, or from a second replica, isn't seen until a restart or the next members scrape. Every request shares those objects, and the `List<Object>` of `Uppdrag.uppgift` and `Uppgift.uppgift` holds Jackson's mutable maps, so they must only be read. The first load holds the lock for its whole read, so with Postgres away and nothing cached, requests wait out the 5-second `connection-timeout` one after another. Activity isn't cached
- A re-scrape doesn't replace a local database: activity is only fetched for the latest two terms, and `riksdag_*` is curated. Nothing else holds a copy, so keep the local database rather than re-creating it
- Riksdagen configs (category `Riksdagen`, flows `MEMBER_OF_PARLIAMENT` and `MEMBER_ACTIVITY`) are in `parliament-service`'s database, so they aren't in `/series-config`, which `macro-series-service` serves from its own, and don't appear in the chart picker

### Kommun, region and Riksdag elections (Valmyndigheten)

- All of this runs in `election-service`, on its own database and scrape lock. `MunicipalElections` (KF) and `RegionElections` (RF) scrape the final results from `resultat.val.se`: `index.md5` lists one zip per kommun/region, and only the `mandatfordelning` JSON inside each is parsed (votes, seats, elected members). First run downloads ~310 zips (~1.5 min); later runs skip files whose md5 is unchanged, so corrected files are picked up automatically
- A file that fails, also on valid JSON of an unexpected shape, doesn't stop the others. What succeeded is written, but the item is `FAILED` and stays pending, so the cron retries about once a minute and only re-fetches the failed files, whose md5s aren't stored; a permanently broken file retries until it is fixed. After 5 consecutive failed files the run stops fetching and is handled the same way, so an outage doesn't hold `scrapeLock` for hours; 5 permanently broken files in a row also keep the files after them from being fetched. With nothing fetched from any changed file, nothing is written and the item is `FAILED` too. An interrupted thread abandons the run the same way and drops what it had fetched. An index without files only logs a warning and the item is marked done, because a new election's folder has no `slutlig` files until the results are final
- `ParliamentElections` (RD) uses the same pipeline, but its single zip (`s/rd/..._00_RD.zip`) holds all 29 valkretsar under `valkretsLista`, so the parser returns one area per valkrets (area code `01`..`29`, Gotland is `09`). Valkrets seats include the utjämningsmandat assigned to that valkrets (they sum to 349). The ~200 MB per-district `rostfordelning` file in the zip is streamed past, not parsed
- `scrape_url` (`.../resultatfiler/val2026`) selects the election; point it at the next election's folder with a migration. Gotland has no regionfullmäktige
- Who governs (`local_governance`) has no open data source and starts empty; add rows by migration (party abbreviations as in the results). The frontend only shows the "styre" section where a row exists
- Configs use category `Valmyndigheten` and flow `LOCAL_ELECTION`. They are in `election`'s database, so they are not in `/series-config` either
- Riksdag parties get the colours of parliament's `GET /macro-analyzer/parliament/parties` ([ADR 0005](docs/adrs/0005-cached-rest-between-services-and-no-message-broker.md)); other parties keep Valmyndigheten's colour, then gray. `RefreshingPartyColorAdaptor` (behind `PartyColorPort`) holds the list in memory, so a request never calls parliament. `ParliamentPartiesClient` fetches it on the adaptor's own daemon thread, independent of `scheduler.enabled`: first when the application is ready, then every `election.parliament.refresh-interval` (1h), or every `retry-interval` (15s) until a first list has loaded. `timeout` (5s) covers the whole exchange. A failed refresh, a 204 or an empty list keeps the list held; with no list, Valmyndigheten's colours are used. `election.parliament.url` (env `ELECTION_PARLIAMENT_URL`) defaults to `parliament-service` under `mvnw`, `http://localhost:8084`; Compose sets `http://parliament:8084`. `election-service` has no `depends_on` on parliament and starts without it. With no list yet, the colours load at the next retry after parliament is up, at most 15 seconds later
- `macro-backend/contracts/parliament-parties.json` is the contract for that endpoint: the fields election reads. `ParliamentPartiesClientTest` and `PartiesContractHttpTest` hold each side to it, using only the file and HTTP. Changing `code` or `color` needs care, because `/parliament/parties` is an API between services

### Accounts and login (`auth-service`)

- Decided in [ADR 0010](docs/adrs/0010-own-auth-service-with-sessions-and-jwts.md), and described as a whole in [`docs/authentication.md`](docs/authentication.md). All of it is under `/macro-analyzer/auth/`: `POST register` (`{email}`, always 202 for a valid address, so it doesn't tell which have accounts), `POST register/complete` (`{token, displayName, password}`), `POST password-reset` (`{email}`, always 202 for a valid address), `POST password-reset/complete` (`{token, password}`), `POST login` (`{email, password}`; sets the session cookie and answers `{accessToken, expiresInSeconds, user}`), `POST token` (a new JWT from the session cookie, 401 without a valid one), `POST logout` (204) and `GET jwks.json` (the public keys)
- There is no Spring Security filter chain: the controller reads its one cookie. `AuthApplication` scans `auth` and `shared` only, so `scrape`'s beans, crons and migrations stay out. Its database therefore has no `series_configuration`, and `BackendService.AUTH` has `scrapes = false`, which keeps the acceptance harness's redirect of the sources away from it
- The account only exists once the mailed link has been used, so `app_user` has no unverified rows. `email_token` and `user_session` hold SHA-256 hashes of their tokens. A request for an address that gets no mail still stores a token, whose value is discarded, so both cases take the same time. Expired rows are deleted when a new one of that kind is written. At most one mail per address and purpose per `auth.email-token-resend-interval` (1 min), and a new link replaces the old one
- Links in mails start with `AUTH_PUBLIC_URL` and carry the token in the fragment (`/konto/registrera#token=...`, `/konto/aterstall-losenord#token=...`), so it reaches neither the access log nor Loki
- `AUTH_ADMIN_EMAIL`: that address's account gets `ADMIN` at registration and at every start. Removing the variable doesn't demote it
- `AUTH_MAIL_MODE=log` (the default) writes each mail, with its link, to the service's log, and from there to Loki if the observability stack runs. `smtp` needs `SPRING_MAIL_HOST`, `SPRING_MAIL_PORT`, `SPRING_MAIL_USERNAME` and `SPRING_MAIL_PASSWORD`, and Compose requires STARTTLS. A failed send is only logged
- `AUTH_COOKIE_SECURE` defaults to `true`, which works over plain http on `localhost` in Chrome and Firefox, and needs https anywhere else
- The signing key (ES256) is generated at the first start and kept in `signing_key`. The newest row signs, and every row is published
- Every other service verifies the JWT on its `macro.scrape.path-prefix` only (`ScrapeSecurityConfiguration` in `scrape`, Spring Security's resource server), and requires `ADMIN`. There is no filter chain on any other route, so a stale token can't turn a read into a 401. Spring Security's firewall does apply to every request, so a path with `;` or an encoded slash answers 400. The issuer and audience are `macro-hub-auth` and `macro-hub`, in both `NimbusAccessTokenAdaptor` and that class. The keys come from `auth.jwks-uri` (env `AUTH_JWKS_URI`) at the first token, so a service starts without `auth-service`, and a scrape call answers 500 while the keys can't be fetched (the fetch has 5-second timeouts, which don't cover DNS). The crons don't go through HTTP. `auth-service` excludes the resource-server starter from `macro-platform`, or Boot would lock all its routes
- An existing volume needs the `auth` database created first, with the `01-service-databases.sh` command under "Starting the local stack". **`auth`'s database holds the only copy of the accounts**

### SCB regional statistics (DeSO / RegSO)

- All of this runs in `regional-statistics-service`, on its own database and scrape lock. `ScbRegionalStatistics` (category `SCB`, flow `SCB_REGIONAL`) scrapes curated indicators from SCB's PxWeb API v2 (`scrape_url` `https://statistikdatabasen.scb.se/api/v2`, CC0). Indicators live in `scb_indicator` (seeded by the service's `V1`): `numerator`/`denominator` are JSONB lists of `{table, contents, select}`; every table dimension except `Region` and `Tid` must be selected, codes within a dimension are summed, a later source replaces an earlier one per year and version, and with a denominator the value is `sum(num) / sum(den) * multiplier`
- One SCB table holds every area version; the region code tells them apart: `DeSO2018` (`0114A0010`), `DeSO2025` (`0114A0010_DeSO2025`), `RegSO2020` (`0114R001`), `RegSO2025` (`0114R001_RegSO2025`). Data is requested per version with a PxWeb wildcard (`?????????`, `*_DeSO2025`, …) and chunked by year to stay below 150 000 cells per call. Years a version has no data for are 0/null placeholders in SCB; a (version, year) is only kept when a value is non-null and non-zero. `area_code` is stored without the suffix so it matches the boundary files
- `scb_table_state` keeps SCB's `updated` stamp per table; an indicator is skipped when all its tables are unchanged and it already has rows. Stamps are written once every indicator of the run is stored; a table whose fetch failed, and every table of an indicator whose write failed, loses its stamp so the indicators using it are fetched again. To change an existing indicator's selection, also delete its `scb_area_value` and `scb_availability` rows in the migration so it is re-fetched (whether an indicator has data is read from `scb_availability`, which the persister keeps in step with the values)
- Calls are spaced by `scb.delay-ms` (default 350 ms, SCB allows 30 calls per 10 s) and retried up to 8 times: some SCB servers intermittently answer "Non-existent table" (404/400) for tables that exist. A first full scrape takes 9 to 12 minutes (2.4 M rows, ~370 MB; 8 min 49 s when last measured) because SCB spends several seconds on each uncached DeSO request; a run with unchanged tables takes about 15 to 30 seconds
- A full scrape keeps every fetched value in memory until the persister runs (~2.4 M values plus the per-source maps; the container peaked at 846 MiB in a measured first scrape, on a JVM free to use a quarter of 31 GiB, so that's an upper bound rather than what it needs). Under Compose the JVM has no `-Xmx` and the container no memory limit; if either is added, leave room for this or the first full scrape can run out of memory. Under a 1536 MiB container limit, on the since-removed Kubernetes deployment, that scrape peaked at 1348 MiB with the Serial collector, which the JVM picks by itself below 1792 MiB ([ADR 0007](docs/adrs/0007-remove-the-kubernetes-deployment-until-its-needed.md))

### Database

PostgreSQL 16, one database per service on one instance. Each service runs Flyway twice on start-up: `macro-platform`'s `db/platform` (`series_configuration`, `scrape_action_queue`, history table `flyway_platform_schema_history`), which `PlatformFlywayConfiguration` always runs first, then its own `db/migration`, whose `V1` is a squashed baseline with its config rows (a baseline at version 0, set in each service's properties, lets it run on the non-empty schema; without it the start-up fails with "Found non-empty schema(s)"). JOOQ generates type-safe table access, one model per Maven module. Every database has its own `series_configuration` and `scrape_action_queue`. The other tables: in `election`, `local_election_area`/`local_election_party_result`/`local_governance`; in `parliament`, `swedish_members_of_parliament` (JSONB), `swedish_member_activity`, `riksdag_party`/`riksdag_election`/`riksdag_election_result`/`riksdag_organ`; in `regional_statistics`, `scb_indicator`/`scb_area_value`/`scb_availability`/`scb_table_state`; in `macro_series`, the 41 rate, bond, bill, exchange-rate, Fed and Eurostat tables.

The 41 tables in `macro_series` hold one row per series and date: `UNIQUE (date)`, or `(series_name, date)` in `fed_series` and `eurostat_national_debt_series`, from `macro-series-service`'s V2 (the column is `usd_sek_date` in `exchange_usd_sek` and `policy_rate_date` in `policy_rate_sweden`). `MacroPointScraper` keeps the scraped points whose value and date aren't both stored, and `MacroPointUpsert` writes them with `ON CONFLICT ... DO UPDATE`: a revised value replaces the old one and sets `updated`, while `id`, `global_id` and `created` stay. A write of a value already stored changes nothing, so a repeated or retried scrape, or two at once, can't add rows or rewrite them. A new chart series table needs the same constraint and writer.

Chart series in `macro_series`' `series_configuration` carry picker metadata, returned by `/series-config`: `category` (`Räntor`, `Statsobligationer`, `Statsskuld`, `Valuta`, `Nyckeltal USA`), `subcategory` (e.g. `Styrränta`, `Euromarknadsränta`, `Statsskuldväxel`, `Nominell`), `unit` (short Swedish display form taken from the source: `%`, `% av BNP`, `mn EUR`, `mn USD`, `mdr USD`, `SEK/USD`, `punkter`, `index`), `country` (Swedish name, null when not country-specific) and `maturity_months` (rates/bonds/bills only). A new chart series must set them, and `scrape_flow = 'MACRO_POINT'`, in its migration; the chart series are exactly the `MACRO_POINT` configs. `ChartSeriesConfigIntegrationTest` checks that every chart series has a unit and subcategory, and lists the exact category set and row count. `ElectionApplicationTests` checks the flow of the election configs, and `ParliamentApplicationTests` of the Riksdagen ones. `/series-config` lists the configs in `id` order, and `/chart-data` gives a series its colour from its place in that order rather than the request's, so the baselines keep the ids the rows had before the split.

Every service uses Spring Boot's auto-configured HikariCP pool and jOOQ `DSLContext` (`spring.jooq.sql-dialect=POSTGRES` in its properties), and there is no connection code of its own. jOOQ's transactions run through Spring's transaction manager, on one connection per transaction, and a read on another thread doesn't wait for one or see its uncommitted changes. A SQL error from a statement arrives as Spring's `DataAccessException` (e.g. `DuplicateKeyException`), not jOOQ's, but that isn't the only kind: a `transaction` that can't get a connection throws `CannotCreateTransactionException`, which is a `TransactionException`, and a checked exception inside a transaction arrives as jOOQ's `DataAccessException`. So code that must survive an outage catches `RuntimeException`, as `ScrapeService` and `ScbRegionalPersister` do.

- **Sizes:** at most 8 connections per instance, 2 when idle. Five services at 8 is 40 of Postgres's 100 `max_connections`, plus 1 or 2 for postgres_exporter, which leaves room for a second replica each and a rolling update; add up again before adding replicas. Flyway uses 2 or 3 of them at start-up
- **When Postgres restarts or is re-created,** a service recovers without a restart. Requests in flight answer 500, as do requests that wait out `connection-timeout` (5 s) while it is away. Measured on a Compose stack: back within 10 s of Postgres accepting connections, which is about the JVM's 10 s cache of a failed DNS lookup, as Compose's DNS doesn't know a stopped container's name. A cron run that fails tries again a minute later, and a queue item that failed stays pending, so the next drain retries it. An interrupted `transaction` rolls back, so an SCB indicator keeps its old values. An SCB run that wrote at least one indicator is marked as done, though: a failed indicator loses its table stamps and is fetched again on the next enqueue, normally the 22:00 cron, not on the next drain
- **What this doesn't cover:** a Postgres on another host that vanishes without closing its connections. Idle connections are tested when borrowed, but with no `socketTimeout` a running query hangs. During a scrape, `ScrapeService`'s `scrapeLock` then stays held, so that instance's scrapes stop until it is restarted
- **A long write isn't cut off:** `connection-timeout` is only for getting a connection, and `max-lifetime` (default 30 min) waits until a connection is back in the pool. A `socketTimeout` below the longest SCB write would cut that write off, which is why there is none
- **At start-up nothing changes:** a service whose database can't be reached fails to start, because Flyway's first connection fails (`initialization-fail-timeout`'s default) and there are no retries. Compose's `depends_on` waits for Postgres

## Testing

- JUnit 5 + Mockito for unit tests
- TestContainers (PostgreSQL) for integration tests — Docker must be running for `mvn test`. `application-test.properties` uses `jdbc:tc:...?TC_DAEMON=true`: every context in a JVM shares that one container, and without `TC_DAEMON` it stops when the pools happen to hold no connection
- `ConnectionPoolIntegrationTest` (one in each service, on its own container) pins the dialect and pool sizes, that the service works again after `pg_terminate_backend` on all its connections, that a concurrent read neither waits for nor sees an open transaction, and that a start-up with an unreachable database fails
- Each Maven module has its own tests. `macro-platform` has the unit tests of `scrape` and `shared`, and its own `ArchitectureTest`. `SeriesConfigRepositoryTest` is in `scrape`'s package but lives in `election-service`, because it needs a running application with migrations; `NoStaticResourceHandlersHttpTest`, `ManualScrapePathsHttpTest` and `ActuatorExposureHttpTest` (metrics answer with the `application` label, the other actuator endpoints 404) are in each service for the same reason. `TestSeriesConfigFactory` and `TestJsonReader` exist in several modules: a shared test-jar would be on the classpath as a jar, and `ArchitectureTest`'s `DoNotIncludeTests` would then import its classes as production code
- `ArchitectureTest` (ArchUnit, one in each Maven module with production code). `macro-platform`'s holds the rules of `scrape` and `shared`. Each service's imports all of `com.kg.macroanalyzer` from the classpath, so it sees `macro-platform` too. In all of them `importIncludesMacroPlatform` fails if the import stops finding its classes, because the rules would then pass silently. See "Dependency rules" below
- Test fixtures in `src/test/resources/json/`
- `@ActiveProfiles("test")` activates `application-test.properties`

### Acceptance tests

`macro-backend/acceptance-tests` ([ADR 0008](docs/adrs/0008-black-box-acceptance-tests-through-the-gateway.md)) starts the packaged system and only talks HTTP through the gateway. Tests are named `*AcceptanceTest` and failsafe runs them in `verify`. The journeys are in the package `acceptance.tests`, and everything they run on (`AcceptanceStack`, `BackendService`, `Gateway`, `Sources`, `Mailbox`, `AdminToken`, `Valmyndigheten`, `Eventually`) in `acceptance.support`. Surefire is off in this module, because its default includes match that name too, so `mvn test` doesn't start the stack. Docker must be running.

- `AcceptanceStack` runs everything with Testcontainers `GenericContainer`s on their own network: `postgres:16` with the real `postgres-init/`, the services (all five of `BackendService.ALL`, started in parallel), WireMock as `sources`, and the frontend's nginx as the gateway. `AcceptanceStack.running()` is the one stack per JVM that most journeys share. A journey that needs clean or unusual state starts its own with `AcceptanceStack.startWith(services)`, as `ParliamentAcceptanceTest`, `ElectionAcceptanceTest`, `PartyColoursAcceptanceTest`, `RegionalStatisticsAcceptanceTest` and `FailureAndRecoveryAcceptanceTest` do, which adds up to half a minute each. Booting the services is most of the suite's time, so a journey that only reads, or whose state another class's stack already has, uses that stack rather than its own: `FreshSystemAcceptanceTest` reads the shared stack's unscraped state, and parliament's stack, which runs no other service, also shows the other services' routes answering 502. The tests of a class run in turn, so one that changes the stack's state, such as `FailureAndRecoveryAcceptanceTest`'s Postgres restart, can share its class's stack if it uses series of its own. `BackendService.withEnvironment(...)` gives a service in such a stack extra environment variables. In a stack without a service, that service's routes answer 502 until `stack.startLater(service)` has started it under its network alias: nginx resolves an upstream per request, with `valid=10s`, so poll the first request. Ports are random and nothing has a volume or a `container_name`, so it can run next to the Compose stack and never touches `docker_pgdata`
- It reuses no Compose file, so a setting changed in `docker-compose-all.yml` isn't seen here. The `compose-smoke` CI job covers that file, see below
- Each service starts once. Flyway seeds `series_configuration` with the real sources' URLs, and an `afterMigrate.sql` callback, copied into the container with `SPRING_FLYWAY_LOCATIONS` set to Boot's default plus the callback's directory, points every `scrape_url` at `http://sources:8080` in the same run, before the configs are read once at start-up. Setup then fails if `psql` in the Postgres container finds a row pointing elsewhere, so a scrape can't reach a real source. Those are the only times the harness touches the database, and the module has no JDBC driver, so a test can't. `SCHEDULER_ENABLED=false` keeps the crons out, and `JAVA_TOOL_OPTIONS` runs the services' JVMs on C1 and the Serial collector, because boots are most of the suite's time and CPU-bound, so the tests don't run on the production JVM settings
- The images are `regional-statistics-service:acceptance`, `macro-series-service:acceptance`, `parliament-service:acceptance`, `election-service:acceptance` and `macro-frontend:acceptance` (`-Dacceptance.image.macro-series=...`, the same for `regional-statistics`, `parliament` and `election`, and `-Dacceptance.image.gateway=...` to use others), so a run doesn't change what a local Compose stack starts. `macro-infra/scripts/acceptance-test.sh` builds them each time, and `mvn -pl acceptance-tests verify` runs against whatever is there, so after a code change use the script. A missing image fails with a message naming the script
- Under snap's `docker`, whose private `/tmp` hides a checkout there from `docker build`, the script fails with `path "macro-series-service" not found`. Run it from a clone under `$HOME`
- Scraping needs an admin: `Gateway` adds `AdminToken` to requests under `/macro-analyzer/scrape/`, signed in the test JVM, and each stack's services read its key from the stub (`AUTH_JWKS_URI`), so a journey doesn't need `auth-service`. Only `AuthAcceptanceTest` uses the real one, with `postAnonymously` and `postWithBearer`. A journey is a test class that uses `AcceptanceStack.running().gateway()` and `.sources()`: `sources.serveJson(path, fixture)` with a fixture from `src/test/resources/sources/`, requests through the gateway, then exact values in the answer. `sources.requestCount(path)` shows the stub was hit. A source whose request is told apart by its query, such as Fed or Eurostat, uses the overloads with a query map, `sources.serveJson(path, query, fixture)` and `sources.requestCount(path, query)`, because a stub that ignores the query would hide a wrong URL: with them, a wrong URL gets the stub's 404 and the chart answers 204. `sources.serveJsonBody(path, body)`, also with a query map, serves a body built in the test, such as dates computed from today. Test classes run at the same time, at most 4 (`src/test/resources/junit-platform.properties`), and the tests of a class in turn. So logs interleave, a service's lines start with their class and stack (`Election-3/election`), and `-Djunit.jupiter.execution.parallel.enabled=false` runs them one class at a time, for reading them. `max-pool-size` is what enforces the limit, not `parallelism` alone. In the shared stack only one class may drain a given service, as a drain during another answers 409. Nothing on it scrapes regional statistics, parliament or elections, nor the chart series `FreshSystemAcceptanceTest` asks for, because that class asserts they are still empty. There each journey uses its own series or area, because a failed queue item stays pending and every later drain retries it, and asserts nothing that another journey's scrape would change. Parliament has one list of members and no series or area to keep apart, so its member journeys own their stacks, and on the shared stack nothing but the parties and elections is read from it. Election's lists answer for every area and all three types read one `index.md5`, so its journeys own their stacks too: `Valmyndigheten.publish(sources, files...)` serves the zips, built in the test from a `mandatfordelning` fixture with `Valmyndigheten.ResultFile`, and an index with their real md5s, through `sources.serveBytes` and `sources.serveText`. Colours of Riksdag parties aren't asserted there, since they depend on parliament's list. `PartyColoursAcceptanceTest` does that, with parliament running, absent and started late: election fetches the list in the background, so it polls with `Eventually.assertWithin` and sets `ELECTION_PARLIAMENT_RETRYINTERVAL` to 1 s. A scrape walks every SCB indicator, and a table that answers an error costs 25 s of retries, so `RegionalStatisticsAcceptanceTest` owns its stack as well and only serves `households`' table: `sources.serveJsonForOtherPathsMatching(regex, fixture)`, below the default stub priority, answers every other table's metadata without the dimensions its indicators select, which fails them at once. That table has no other indicator, so those failures don't drop its stamp. A data stub matches the region wildcard of one boundary version, and `SCB_DELAYMS=0` turns the throttle off. `FailureAndRecoveryAcceptanceTest` uses `sources.failWith(path, status)` and `sources.serveJsonDelayed(path, fixture, delay)`, and doesn't assert the answer of a drain whose items fail, which is 200 regardless. It holds a scrape open with the delay and polls `sources.requestCount` to know that it has started, as WireMock logs a request before delaying its answer. `stack.stopPostgres()` and `stack.startStoppedPostgres()` keep the container, and so the anonymous volume with the data, which `GenericContainer.stop()` would remove. Another service joins as a `BackendService` constant in `ALL` and a `docker build` line in the script
- `macro-infra/scripts/compose-smoke.sh` is the `compose-smoke` CI job, and **it only runs in CI: it refuses without `CI=true`, and also when the `docker_pgdata` volume or `macrohub-postgres` container exists, and must not be run locally**, because it would collide with a local stack and could share `docker_pgdata`. It builds the service images as `:latest` on the runner, copies `.env.example` to `.env` and starts the real `docker-compose-all.yml` on an empty volume, with `macro-infra/scripts/compose-smoke.override.yml`, which only sets `SCHEDULER_ENABLED=false` on the services, so that no cron can call a real source. The script fails before starting anything if a service lacks that. Then, within 5 minutes, each service's route has to answer through `http://localhost:8081`, with the seeded counts (108 series, 11 parties, 26 indicators), and an unknown path has to answer 404. It scrapes nothing, and the job takes about 2 minutes. A new chart series, party or indicator changes those counts, here as in `FreshSystemAcceptanceTest`

## Workflow

Agreed changes are implemented with the `/ship` skill (`.claude/skills/ship/SKILL.md`): the agent the user is talking to implements the change and opens a PR (a separate implementer sub-agent does, only if the user asks for one), a separate reviewer sub-agent (Fable, or Opus when Fable credits run out) reviews it, then it is merged once the reviewer says LGTM. `main` is protected: every change needs a PR, and the `frontend` and `backend` jobs in `.github/workflows/ci.yml` (frontend: tracked-`.env` check, `npm run typecheck`, build, lint; backend: `mvn test`) must pass. No approval is required. The `acceptance` job (`macro-infra/scripts/acceptance-test.sh`) also runs on every PR and isn't a required check ([ADR 0008](docs/adrs/0008-black-box-acceptance-tests-through-the-gateway.md)), so read its result before merging. So does the `compose-smoke` job (`macro-infra/scripts/compose-smoke.sh`), which starts the real `docker-compose-all.yml` and isn't required either.

Larger decisions are recorded as ADRs in `docs/adrs/`. The finished [migration guide](https://github.com/KGjertsson/macro-hub/blob/584119f/docs/microservice-migration-guide.md), at its last version, records how the backend was split into services. To add one, follow [`docs/adding-a-service.md`](docs/adding-a-service.md).

PRs also get an automatic Claude review comment from `.github/workflows/claude-review.yml` (comment-only, not a required check; a PR that changes that file is skipped, since the action requires it to match `main`). It needs the Claude GitHub App installed on the repo and a `CLAUDE_CODE_OAUTH_TOKEN` repo secret generated with `claude setup-token` (Pro/Max subscription).

## Code comments

- No comments that describe what the code does: no restating, and no summaries of classes or methods, including Javadoc/TSDoc and section labels. Express it through names and structure.
- A comment is allowed, rarely, on complicated code to explain why it looks the way it does: a non-obvious constraint, an external system's quirk, a workaround.
- `// given`, `// when` and `// then` in tests stay.

## Commit Convention

Follows conventional commits: `feat:`, `fix:`, `refactor:`, `test:`, `config:`, `chore:`, `docs:`
