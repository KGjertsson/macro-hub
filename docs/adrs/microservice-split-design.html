macro-hub microservice split

The design for one service per business domain, based on the code at 07c7482 and the row counts in the local database. The decisions were made on 2026-11-01. The app isn't deployed anywhere yet.

In short: four services behind a gateway, one Postgres instance with one database and role per service, and scrape code as a shared library. The only runtime call between services is election asking parliament for party colours, which is a cached REST call. No message broker is needed. Docker Compose runs it locally, and Kubernetes is the eventual deployment target.

The ADRs are authoritative if they ever differ from this page.

Where the scrape module goes

scrape is the one module that doesn't map cleanly to a service, and this is the main design decision in the split. It holds no business data, and every domain plugs into it in-process through RegisteredScrapeFlow.

The price of B is that the global enqueue-all no longer exists. Nothing in the frontend calls the enqueue or scrape endpoints, so a small script that calls each service covers it. A central scrape dashboard would be the one reason to reconsider.

B also replaces today's single scrapeLock, which makes every domain wait for a running scrape. Each service gets its own lock, so a 12-minute SCB run stops delaying the others. All four would start at 22:00 and write concurrently, so stagger the cron hours if that strains Postgres.

How to store the data

The data is already nearly partitioned. No foreign key crosses a domain, and the only tables used across domains are series_configuration and scrape_action_queue. Those split cleanly: configs by scrape_flow, queue rows by series name.

The shared instance remains a shared point of failure, and a heavy SCB write can still slow the others. That's a fair trade for one replica of each service. A service can move to its own server later by moving its database and changing its URL, for example if regional-statistics' load ever hurts the others.

Nothing is deployed, so today's shared database only exists on development machines. A new database starts empty and is re-scraped by default. Dump and restore per domain only saves time locally, mainly because the first SCB scrape takes about 12 minutes. Backups are per database once there is something to back up.

What changes in the tooling

  • Flyway: each service's database gets its own history table and starts from a squashed baseline of its tables and seed data. V1–V32 stay in git history as the record of how the shared database got here. A new database needs its role and database created first, and Postgres init scripts only run on an empty data volume.
  • jOOQ: each service generates a model from its own database only, so a query on another domain's table no longer compiles.
  • Queue and config tables: macro-platform ships their DDL and its jOOQ model, and each service applies them in its own database. Their migrations run in a separate Flyway run with its own history table, before the service's own.
  • Tests: ArchitectureTest shrinks to one per service plus Maven module boundaries. ChartSeriesConfigIntegrationTest moves to macro-series, and its checks on other flows move to their owners.

A cache suits this data because riksdag_party only changes through Flyway migrations (V22 and V24 so far). No scraper writes to it. The call would be needless if election kept its own copy of the colours, but then a new party or colour would need two migrations.

Kafka stays out. kubernetes_setup.sh still installs it, but the application doesn't use it, and it would be the largest process in the cluster with one low-value message to carry.

What it costs

The modules are already well separated, so the code move is the easy part. The ongoing cost is operational, for what is about 10,000 lines of Java running as one replica.

  • Memory: a docker stats reading of the monolith showed 609 MiB, a number that moves with the JVM's heap (another reading showed 890 MiB). Four JVMs would plausibly take 1.5–2 GiB. That is an estimate rather than a measurement, and it matters if this runs on small cluster nodes.
  • Local dev: the start-up sequence becomes four services and a proxy, so docker-compose-all.yml becomes the default route and runs all services at each stage.
  • Deploys: four images, in Compose now and in Kubernetes manifests at the first deployment, and CI should build only what changed. A change to macro-platform still rebuilds everything.
  • What you get: scrapes that no longer block each other, SCB's memory spikes isolated, independent deploys, and boundaries enforced by the build and by separate databases.

Migration order

Each step is a separate PR that leaves the app working. The migration guide is the living version of this list.

  1. Prepare inside the monolith. Convert to a Maven reactor, extract macro-platform, and split the nginx routes while they all still point to the monolith.
  2. Extract regional-statistics. It has no dependents and the biggest operational gain, so it proves out the template: create the database and role, fill that domain's data, baseline, config rows, image and Compose service.
  3. Extract macro-series. This is the largest move, but it's mechanical once the template exists.
  4. Extract parliament, and switch election to REST. Election gets the cached HTTP adaptor while it's still in the monolith.
  5. Retire the monolith. What remains is election. Move its data to its own database, rename it and delete the leftovers.
  6. First real Kubernetes deployment. Manifests for all four services, routing, Postgres databases and roles, and image delivery.

Each extraction must delete its config rows from the monolith in the same release, because ScrapeService refuses to start if a config names a flow that isn't registered.

Decisions

  1. 0001: Split the backend into one service per domain
  2. 0002: Keep scrape as a shared library
  3. 0003: One database per service on one Postgres instance
  4. 0004: Keep manual scrape endpoints public for now, an accepted risk to revisit
  5. 0005: Cached REST between services and no message broker
  6. 0006: Kubernetes as the eventual deployment target, with Docker Compose for local development

One choice in the deployment stays open: whether the cluster's gateway is nginx in the frontend image or Ingress routes. The guide lists it with the other open questions.

Note, 2026-11-04: 0007 removed the Kubernetes deployment until it's needed, so Docker Compose is the only way to run the app.
